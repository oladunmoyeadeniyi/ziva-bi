and inlined into the JS bundle during `next build`, not at server start — so setting them only in
the Dockerfile's `runner` stage (or only via Render's dashboard-configured runtime env vars) would
have no effect on a Docker-based build. Placing `ENV` before `RUN npm run build` in the `builder`
stage is the correct fix for that specific failure mode.

**Same render.yaml/Docker inconsistency flagged last round — now two commits in a row assume it,
still unresolved.** `render.yaml` (lines 70-82) still configures `ziva-bi-frontend` with
`runtime: node` and a `buildCommand`/`startCommand` that never touches the Dockerfile, and
`envVars` already includes `NEXT_PUBLIC_API_URL` for exactly that path. If that config is what's
actually live, this fix (and the previous round's `public/.gitkeep` Docker-COPY fix) would be
inert — Render's native `runtime: node` builds *do* expose service env vars to `npm run build`
directly, so the "Failed to fetch" bug wouldn't stem from a missing build-time var on that path

That said, the *symptom* reported in this brief — a successful build that still can't reach the
backend at runtime — is actually corroborating evidence that the frontend is genuinely running
via Docker now (as the prior round's build-stage COPY error also implied): a native

mode at all, whereas a Docker build silently defaulting `NEXT_PUBLIC_API_URL` to
`localhost:8000` (via `apiFetch`'s fallback) matches exactly what's described. Given two
consecutive Docker-specific fixes have now lined up with two consecutive real symptoms, I'm
treating "the live service is on Docker, and render.yaml is stale" as confirmed enough to not
block on — but `render.yaml` should be updated to match reality (or removed/reconciled) before it
