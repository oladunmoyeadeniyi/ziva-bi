## Issues Found (in order of severity)

### 1. CRITICAL — `backend/app/models/auth.py`: `ImpersonationSession` gutted, crashes on import

Not declared anywhere in the brief (brief only mentions `UserTenant.must_change_password` for this
file). The diff shows `ImpersonationSession` lost four columns — `environment`, `entry_point`,
`started_at`, `ended_at` — replaced with a `UniqueConstraint` referencing columns that don't exist
on this table at all:
```python
    __table_args__ = (
        UniqueConstraint("user_id", "tenant_id", name="uq_impersonation_sessions_unique"),
    )
```
(The real columns are `impersonator_id`, `target_user_id`, `target_tenant_id` — not `user_id`/
`tenant_id`.) Confirmed empirically, not just by reading:
```
$ python -c "from app.models.auth import ImpersonationSession"
sqlalchemy.exc.ConstraintColumnNotFoundError: Can't create UniqueConstraint on table
'impersonation_sessions': no column named 'user_id' is present.
```
This fails at **class-definition time**, i.e. the moment `app.models.auth` is imported — which
means `app/models/__init__.py`, every router, and the entire FastAPI app fail to start. This isn't
a narrow regression in one impersonation endpoint; it's a full backend outage. It also destroys the
M9.3b user-impersonation audit trail (previously verified end-to-end and shipped in commit
`1a60a1c`) — `platform.py`'s impersonate/end-session endpoints construct
`ImpersonationSession(..., environment=..., entry_point=...)` and set `.ended_at`, all of which
would break even if the constraint were fixed.

**Fix:** restore the four deleted columns exactly as they were; delete the bogus
`__table_args__`/`UniqueConstraint` entirely — nothing in this brief calls for a uniqueness
constraint on impersonation sessions, and one wouldn't make sense semantically (a user can be
impersonated multiple times).
