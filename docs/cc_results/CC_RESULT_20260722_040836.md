## Architectural notes
This is the same *class* of from-scratch-DB bug as the previous round's `b0c1d2e3f4a5` ordering
fix, but a different failure mode: there, two sibling branches raced on tie-break order; here, a
migration was written and applied against a dev DB *before* an earlier-inserted ancestor
(`a1b2c3d4e5f7`) existed in the graph, so it never had to coexist with that ancestor's effects until
now. Conditional SQL is the right fix (rather than re-pointing `down_revision`, which wouldn't help
here since the two migrations perform overlapping — not just misordered — work). This is the tenth
consecutive commit in the deployment push and, per the brief, the next concrete error a from-scratch
Render deploy would hit after the previous fix cleared the `finance_review_steps` ordering issue.
