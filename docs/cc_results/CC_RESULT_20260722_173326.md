## Important finding — same crash pattern exists in two other files, untouched by this fix
While checking whether other code paths share the root cause (duplicate system roles in
production), I grepped for the same query shape (`Role.name == ..., Role.tenant_id.is_(None)`)
combined with `scalar_one_or_none()` and found two more instances this commit does **not** fix:

- `backend/app/routers/invitations.py:159` — role lookup during **invite acceptance**
  (`role = role_result.scalar_one_or_none()`)
- `backend/app/routers/tenant.py:465` — role lookup inside a loop when **assigning roles to a
  user** (`role = role_result.scalar_one_or_none()`)

Both will raise the identical `MultipleResultsFound` crash under the same condition (a duplicated
system role name) that this commit just fixed for signup. Since the brief's post-deploy SQL script
permanently deduplicates the `roles` table, these become safe once that script runs — **but there
is a window after this deploy and before the manual SQL is run** where duplicate rows still exist
in production. Given `/invite/accept` was just fixed for an unrelated build bug two commits ago and
is presumably about to see real traffic, if anyone accepts an invite for a role name that's
currently duplicated (e.g. `tenant_admin`) during that window, they'll hit the same crash at a
different endpoint.

**Recommendation:** run the post-deploy dedup SQL immediately after this deploys, before relying on
invite-accept or tenant role-assignment in production. Not blocking this commit — the two files in
scope are correct and complete for what they claim — but flagging so this doesn't get rediscovered
the hard way.
