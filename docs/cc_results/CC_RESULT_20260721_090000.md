## Why I'm blocking instead of approving
Last round I explicitly reviewed the SSL fix and called out `ssl.create_default_context()` as "the
correct, secure choice... not a disable verification shortcut." This round's fix removes exactly
that property — `verify_mode = ssl.CERT_NONE` combined with `check_hostname = False` means the
connection is encrypted but **completely unauthenticated**: the client will accept a certificate
from *any* server claiming to be the database, self-signed or not, with no way to detect if the
connection has been intercepted. This isn't a stylistic concern — an encrypted-but-unauthenticated
connection is vulnerable to an active machine-in-the-middle attack that can read and modify every
query and result, including credentials, session tokens, and all tenant financial data, without
either endpoint detecting anything wrong.

This matters more than it might for a purely internal/private-network hop, because two commits ago
`internalConnectionString` was reverted to plain `connectionString` (confirmed as the only valid
`fromDatabase` property) — meaning this connection now travels over the **public internet** to
Render's external hostname (`dpg-xxx.oregon-postgres.render.com`), not a private VPC-style link.
Certificate verification is the only remaining protection against interception on that path.

## The likely real root cause — and a safer fix to try first
The OpenSSL error string `"self-signed certificate"` is what Python reports whenever it cannot build
a trust chain to a known root — and critically, **this exact message appears whether the certificate
is truly self-signed, or whether it's legitimately CA-signed but the verifying environment's trust
store is incomplete.** `ssl.create_default_context()` relies on the OS-level CA bundle, and minimal
container/buildpack images (which is what Render's Python runtime almost certainly is) frequently
ship an incomplete or outdated one. This is one of the most common causes of exactly this error in
containerized Python deployments — and it's fixable without giving up verification at all.

I checked whether a safer alternative is readily available in this codebase: `certifi` is already
present (confirmed via direct import in the venv) as a transitive dependency of `httpx`, which is
already a direct entry in `requirements.txt` — so it's guaranteed to be installed on Render too, no
new dependency needed. The standard fix for this class of error is to explicitly load `certifi`'s
actively-maintained CA bundle instead of relying on the OS default:

```python
import certifi
ssl_ctx = ssl.create_default_context(cafile=certifi.where())
```

This keeps full certificate and hostname verification intact while fixing the actual likely cause
(an incomplete trust store), rather than removing the protection entirely.
