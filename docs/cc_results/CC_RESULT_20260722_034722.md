## Architectural notes
This is a well-known and easy-to-miss class of Alembic bug: two migrations that are both direct
children of the same parent revision form parallel branches, and Alembic's topological sort breaks
ties between such branches alphabetically by revision ID — not by any awareness of cross-branch
foreign key dependencies. `finance_review_steps` (`b...`) sorted before `approval_engine` (`e...`),
so on a *fresh* database applying all 75 migrations from scratch for the first time, Alembic tried
to create `finance_review_steps` (with its FK to `approval_policies`) before `approval_policies`
itself existed. This would never surface on any environment that applied migrations incrementally
over time in the order they were authored (local dev, or any environment migrated step-by-step as
each PR landed) — it's specific to a from-scratch apply, which is exactly what a first Render
deployment is. Declaring the dependency explicitly via `down_revision` is the correct fix, and I
verified the resulting graph is sound rather than just accepting the brief's summary numbers.

This is the ninth consecutive commit in this deployment push, and the first that isn't
connectivity/SSL/config related — it's the next real error a fresh database migration run would hit
once the connection itself succeeds. Worth checking whether this gets the deploy fully across the
line.
