## Issues Found

### 1. Non-blocking but real — the brief's claimed "safety net" is dead code, and creates a UI gap for an edge case

Brief text: *"hidden modules are excluded from both Subscribed and Available sections entirely;
detail panel retains mode gate banner as safety net."*

Tracing the actual logic in `modules/page.tsx`: `visibleModules = modules.filter((m) =>
isAvailableForMode(m.module_key, postingMode))`, then both `subscribed` and `available` are built
from `visibleModules` — so a module incompatible with the current mode is never rendered as a
`ModuleCard` at all. `selected` can only be set via a card's `onClick`, so it can never be an
incompatible module's key through normal use. That means:
- The `incompatible` prop passed to `ModuleCard` (lock icon / amber warning icon) can never
  actually be `true` for any card that gets rendered — dead code.
- The detail panel's amber "mode gate" banner (`!isAvailableForMode(selectedMod...) && postingMode`)
  can never fire, because `selectedMod` is always drawn from an already-mode-filtered click.
- The "module is active but mode changed — allow deactivation only" branch (explicitly written to
  handle a module that was activated in Connected/Full ERP and later became incompatible when the
  tenant's mode was downgraded to Lite) is also unreachable for the same reason.

**Concrete failure scenario:** a Full ERP tenant activates Accounts Payable. An SA later downgrades
the tenant's posting mode to Lite via the platform system-config panel (unrelated endpoint, already
shipped). AP is still `is_licensed=true, is_active=true` in the database — nothing in that downgrade
path deactivates it. On this page, AP now vanishes from *both* Subscribed and Available (it fails
`isAvailableForMode`), with no card to click, no warning, and no way to deactivate it from here. The
brief's own "safety net" framing implies this exact scenario should surface a warning and a
deactivate path — it does not, because the filtering happens one level above where that logic lives.

Not a hard blocker: `PATCH /api/platform/tenants/{id}/system-config` (SA portal) already has a
license-revocation path that auto-sets `is_active=False`, so the orphaned module isn't a permanent
dead-end — just invisible on this particular page, which is otherwise the primary place an admin
would look. Worth a decision: either (a) keep a card visible for active-but-incompatible modules
(reintroducing the deactivate-only path, matching what the brief's own prose describes), or (b) if
full hiding is the actual intent, update the brief/commit message to drop the now-inaccurate "safety
net" claim. Either is fine — just flagging that the current code and the current prose disagree.
